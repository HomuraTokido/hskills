# AI 时代开源仓库准备指南（oss-ai-readiness）

## 执行边界

- **先区分评估、制定计划、实施整改与公开发布**：本指南不自动授权修改架构、增加配置档位、选择许可证或推送公开仓库。
- **按条件适用，避免照清单过度施工**：检查结果应注明**适用、不适用及具体依据**——说明在什么条件下、为了解决什么问题才需要该项改造，而不是要求所有项目机械套用全部条目。

开源仓库面向两类不同的读者：
- **人类读者**：看门面是否清晰、值不值得试、顺着最短路径能不能跑出可观察的结果；通常不会逐行品鉴内部实现。
- **外来 AI（用户请来二开、接入或排障的 agent）**：会逐行读源码、搜符号、看注释。代码命名、模块边界与注释，就是给外来 AI 看的上下文引导。

## 核心原则

### 1. 双读者代码规范（人类看门面，AI 读源码）
- **自解释符号**：公开接口、核心模块与关键函数使用直白、语义化的名字，减少只有原作者才懂的缩写。
- **写明受保护的性质与验证方式**：在关键状态机与边界条件处，写明为什么这样设计、**受保护的性质是什么，以及如何验证替代实现**；不要只写“不能改”，防止过去的实现限制被外来 agent 当成永久不可改变的架构要求。
- **注释同样属于公开内容**：公开源码中的注释与文档会一起被发布。是否保留某段历史注记，应看其内容本身是否适合公开，而不是只看它是否出现在运行时输出。

### 2. 渐进式采用（完整体验默认，通用能力可独立使用）
仅当项目同时提供通用能力（A）和有鲜明主张的完整闭环（A+B）时适用：
- 默认呈现作者推荐的完整体验，让用户直接理解项目的独特价值。
- 提供清楚可见的轻量入口（如配置开关或轻量档位），让只需要 A 的用户可以独立使用，无需先接受整套工作方式。
- 说明完整闭环解决什么额外问题，以及如何从轻量模式切换，用户可以按实际需要采用。
- 若完整模式确实涉及额外授权，按具体操作处理授权；功能档位本身不替代授权。

### 3. 去个人环境强耦合，保留作者风格
开源后，用户应能在自己的环境里使用项目，无需复刻作者的机器、目录和私人资源。
- **运行所必需的环境差异应有明确入口**：路径、凭据、服务地址等通过配置、参数或合理的自动发现处理，不写死作者机器上的值。可选依赖未配置时正常降级，并在相关功能或状态查询中说明未启用；显式配置无效或操作依赖该能力时，给出可操作的错误。
- **作者风格可以保留**：称呼、视觉主题、角色元素和默认偏好不必为了开源统一改成中性风格。用户有实际替换需求时，再提供配置入口。
- **区分风格与私人依赖**：可以保留作者设计的外观与表达，但不能要求用户拥有作者的私有素材目录、私人账号或仓库外脚本。需要这些资源的功能，应提供公开可用的获取方式、替代方案，或明确作为可选扩展。
- **不为每个个人元素增加配置项**：固定保留、直接移除和开放配置都可以；根据产品定位与实际使用差异选择。

### 4. 公开接口在首次发布前对齐
首次公开前，应检查用户会接触的命令、配置、环境变量与文档，使同一个概念保持一致，避免用户猜测它们之间的关系。
- **同一概念采用一致的名称和含义**：默认值、取值范围和行为在不同入口中保持一致；存在覆盖关系时，明确优先级。
- **遵循各类接口的惯例**：环境变量使用项目专属前缀以避免冲突；CLI flag 和配置键按各自作用域组织，不要求机械复制环境变量前缀。
- **示例与实际接口一致**：README、示例配置、帮助信息中的命令和键名应能直接使用。
- **发布前解决已知命名混乱**：不要求预先设计所有未来接口，但避免把已经发现的不一致留给公开后的用户承担迁移成本。

### 5. 多仓库按真实依赖组织
拆成多个仓库，不意味着每个仓库都必须成为独立产品。
- **独立工具应能单独安装和使用**：不因属于同一生态就强制安装其他无关组件。
- **插件、适配器和扩展可以依赖宿主**：但应明确所需宿主、兼容版本与安装顺序。
- **如实声明依赖边界**：可选集成不应成为基础功能的隐性前提；必需依赖则应如实声明，不用“松耦合”的表述掩盖实际要求。
- **职责与起点清晰**：各仓库说明自身职责，以及何时需要配合其他组件，让用户知道该从哪里开始。

### 6. 提供最短、真实的首次成功路径
用户应能快速判断项目是否值得使用，并通过一条经过验证的路径获得可观察的结果。
- **门面展示具体价值**：有视觉界面的项目优先提供截图或演示；CLI、库和基础设施项目可以用终端输出、输入输出示例或简短调用展示效果。
- **Quickstart 只保留首次成功必需的步骤**：明确前提、命令和预期结果。以缩短真实上手成本为目标，不虚构时间承诺。
- **尽量减少首次运行的依赖**：能用单后端、本地示例或零外部服务跑通时，优先提供；确实依赖外部服务时，说明最小配置、账号与费用前提。
- **明确演示与 mock 边界**：模拟数据或 mock 可以帮助体验，但应说明它验证了什么，以及真实接入还需要哪些步骤。

### 7. 覆盖实际发布范围、历史与授权
检查不能只停留在当前工作区文件：
- **覆盖真实发布物**：`.gitignore` 不会移除已跟踪文件，也不会清除 Git 历史中的内容。若会公开历史，检查范围应包含 Git 历史；若会发布安装包（如 npm/PyPI 包），还需检查实际打包产物。
- **非开源起步项目优先单 commit 发布**：如果项目最初并非按公开标准建立、历史中可能混有临时文件或私人记录，与其冒险洗历史，不如将完整旧历史保留在私有备份中，在公开仓库以整理完备的全新单 commit（orphan branch）起步。
- **分开处理“选择协议”与“确认发布权”**：添加一个 `LICENSE` 文件，不代表仓库内的第三方依赖、字体、图片等素材都已经处理完发布授权；需逐项确认实际发布内容的授权状态。

## 开源前评估与检查清单（需注明适用 / 不适用及依据）

1. **发布范围与授权**
   - [ ] 已确认实际发布范围（当前工作区、已跟踪文件、Git 历史/单 commit 起点、安装包内容）
   - [ ] 已确定代码许可证，并确认仓库内代码、依赖与素材具备相应发布权
   - [ ] 源码注释与文档中不适合公开的私人内容已清理
2. **可运行底座与环境耦合**
   - [ ] 包/工程清单已声明入口命令、依赖与最低运行时版本，现有测试通过
   - [ ] 已清理必需路径/脚本对原作者私人环境的硬编码；可选依赖未配置时正常降级并说明未启用
   - [ ] 保留的作者风格不依赖未公开素材或私人账号
3. **接口、采用路径与多仓库**
   - [ ] 命令、配置、环境变量与文档中的名称、默认值及覆盖优先级一致
   - [ ] 若同时包含通用能力与高门槛完整闭环，已提供清楚可见的轻量入口并说明切换方式
   - [ ] 若为多仓库，已如实说明职责、必需宿主与可选集成顺序
4. **门面与 AI 可读性**
   - [ ] 门面展示具体价值，且包含经过验证的最短首次成功路径（含前提与预期结果）
   - [ ] 核心状态机与边界注释写明了受保护的性质与验证方式，而非永久禁令
