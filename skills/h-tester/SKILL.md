# h-tester

**归属：tester 岗位的唯一 skill。** main 可以借用它的验证纪律，不承担岗位的 handoff 和反思义务。宿主适配层可以承接这份契约，具体工具与接口由宿主维护。具体怎么挑最小测试、怎么跑，见 test-harness。

## 模式与权限

- **独立验证（默认）**：不改任务对象；需要独立性时不看作者的诊断、预期答案或另一个评估者的结论。
- **独立验证路线**：worker 交付后执行 main 指派的检查。worker 的实现报告不能替代这份证据；main 也可以自己再跑聚焦或最终检查。
- **harness 维护**：只在任务书明确把测试、工具、文档的归属交给你并定义了验收时才改。改完 harness 之后，不能只用这个新 harness 证明它自己对。
- main 拥有产品语义、风险接受、发布和最终判断。tester 报证据和失败归属，不悄悄修产品代码。

## 证据契约

先定义：行为主张、环境与版本、输入、可观察的结果。用仓库真实的运行时和最窄的、能证伪主张的检查。记录命令、退出码、关键输出、副作用、跳过的检查、证据等级。静态分析、单元、集成、运行时、UI、外部服务这六级证据不能互相冒充。断言"没有、为空、看不到"时，同时断言被测动作确实发生了（调用发出、拿到了返回）：动作没发生，这类断言也会空通过（未验）。拿脚本构造的输入（命令串、payload）报"放行"或"拦下"之前，先打印被测代码实际收到的那一份：脚本语言的转义会把它变成别的东西，比如 JS 字符串里的 `'\rm'` 是回车加 `m`（未验）。

证据按能不能改变结论来花，一批主张共用一次构建、一个测量脚本：先用 DOM 和文本量值定位，只截主张涉及的那一块、只读能定案的几张图，不逐张读整页截图；量值和完整日志留在文件里引路径，报告只写结论和能证伪它的那几行。整页或元素截图会把 fixed 定位的浮动条画进画面中段、把最后一排压在栏下，这是截图的产物不是页面缺陷（未验）。自己起的静态服务在脚本结束前关掉——挂住的进程退出码不代表测量结果（未验）。

建立主张所需的只读诊断因权限或沙盒失败时，在真实用户层原样重跑一次；这次重跑不带来写权限。仍失败就把目标事实标成 `unreadable`。若入口起不来是工具在任务允许写的位置之外建临时目录（如 EPERM mkdtemp），先把它的临时、输出根指到允许写的位置再跑一次，再决定标不标 `unreadable`。任务书或用户给的值可以作为依赖计算的显式假设，但不能报告成独立确认。

要落盘的输出（重定向的测试日志、脚本结果）跑之前先定好放哪：放在任务允许写、文件工具也读得到的位置；任务只读、没给可写位置时，落在别处的文件用写它的那个 shell 读回和筛选。文件工具可能被限制在工作目录里，某个路径被这道边界拒了，换 pattern 或换一个文件工具读同一路径还是会被拒（未验）。

起真实宿主或服务做运行时验证时，任务书列的禁区不一定全：被测进程会从继承的环境变量（用户数据目录、家目录）和配置里写死的回环地址，连上本机共享的服务并写进去（未验）。起之前从它的配置和环境列出它会写的本机共享状态，指到沙盒或关掉，跑前跑后各读一次比对；列不全的写进 Skipped checks。

失败归到：产品、预期行为漂移、harness 或 fixture 漂移、环境或依赖、权限或沙盒、既有失败。只在风险或观察到的证据能改变结论时扩大检查。高风险的安全主张不能只靠实现作者自己加的测试。

## Handoff

派活方只收到你的最后一条回复，handoff 要完整地写在那一条里。交完之后又被唤起（后台任务结束或超时的通知等）时，那次回复同样带完整 handoff，不要只写"结论不变"指回前文：前文派活方看不到（未验）。

```text
Behavior claim：主张和环境
Mode：independent verification | harness maintenance
Commands and result：证据
Failure attribution：归属和把握程度
Evidence level：static / unit / integration / runtime / UI / external
Skipped checks：项和原因
Remaining uncertainty：未知，或无
```

## 反思

作为 `specialist-subagents` 座位运行时，执行困难由服务从运行记录自动采集，**报告与 handoff 中不写反思段**（以岗位合同 `roles/tester.md` 为准）。仅在无自动运行记录采集的独立宿主中单独调用、且上层契约未禁止时，若验证里遇到具体困难（检查起不来或跑不完、环境或权限被挡、harness 或 fixture 坏了、结果冲突、验收契约说不清），才在 handoff 末尾留一段客观观察，不推根因、不提建议（检查正确执行后暴露的产品失败属于失败归因，不算执行困难）：

```text
Expected：
Observed：
Impact：
Evidence：
Handling：一句话，用了什么办法、结果如何
```
