# requirements-doc

需求文档回答一个问题：**做完之后，世界上有哪些看得见、查得到的变化。** 它是写的人和做的人之间的合同，不是想法集、讨论稿或头脑风暴。

之所以要这么严：验收时每一条只有「做到」和「失败」两种结果。一条没落地，要么是做的人错了（没做、做偏、只做了字面），要么是写的人错了（写不出验收、写了做不到的、和别处矛盾）。两种都要记成失败并说清归谁，下一轮才知道该改文档还是该补实现。「没写清楚，所以我跳过了」不是第三种结果，它是做的人的失败：发现不清楚的那一刻就该停下来问。

## 写文档的人

### 只放已拍板的条目

讨论、来龙去脉、原话、比较、「我的补充，未经确认」，统统放进另一份背景记录，需求文档只引用它。原因：两者混在一起，做的人分不清哪一句是要交付的，最后只交付最好验的那几句。

### 标题和引言里的意图，必须有条目承载

章节名、引言、总述里出现的每一个意图（例如「去工作区化」），都要能指到至少一条条目；指不到，就删掉这个说法或者补条目。原因：标题读起来像承诺，实现方却没有任何一条可以验收它，结果就是谁都以为别人做了。

### 每一条写全这五个字段

```text
R<编号>  <一句话标题>
要的结果：做完后谁、在哪、能看到或做到什么（终态，不是过程）
范围：适用哪些表面（桌面 / 无头 / 哪个 preset / 哪台机器）；明确不包括什么
验收：在什么环境、做什么动作、应该看到什么；证据要到哪一级（真实宿主 / 集成 / 单测）
约束：必须遵守的边界；实现方案不写在这里，除非方案本身就是要求
拍板：谁、哪天、原话一句
```

- **一条只交付一件事。** 能分别做完、分别验收的，拆成多条。捆在一起的条目，验收时最容易只完成其中好验的几项，剩下的没人注意。
- **结果写终态，不写形容词。** 不写「尽量」「优化」「更好」「支持 X」，写「重启后打开同一条会话，工作目录仍是切换后的目录」。形容词没有终点，验收时只能凭感觉。
- **引用要自足。** 不写「配套解决 #7」这种没定义的编号，把被引用的内容在本条写全。做的人手上可能只有这一份文档。
- **范围写全。** 同一能力两边都要的写明两边，只要一边的写明另一边不要。不写，做的人就会只做手边方便的那一边。
- **写不出验收的，不是需求。** 退回背景记录，想清楚再进来。

### 交出去之前自查

1. 标题、引言里的每一个意图，都能指到条目编号。
2. 每一条都有「要的结果」和「验收」，验收能由一个没参加讨论的人照着做。
3. 每一条只有一个可交付物。
4. 条目之间没有矛盾；和项目已有规则冲突的，在条目里写明以哪个为准。
5. 每一条都有拍板人和日期。

过不了自查的条目先不交出去。交出去之后再发现，代价是做的人整轮返工。

## 照着它实现的人

- **按意图交付，按字面验收。** 「要的结果」是目标，「验收」是证明。只满足了验收的字面、没达到结果，算失败。验收点是写的人对意图的有限描述，不是意图本身。
- **不清楚就当场停下来问。** 写不出能执行的验收、做不到、或者和别处矛盾的，立刻问写的人。不要自己挑一种解读做下去，也不要跳过。问之前先确认答案确实不在文档和对方说过的话里，省掉一个来回。
- **不要单方面推迟或缩小范围。** 推迟、缩范围、改验收，都要拍板人改条目并写进变更记录。实现方自己定「这条先挂个判据」，等于替写的人改了合同。
- **goal 和任务清单从条目来。** goal 里列条目编号和各自的验收，不另写一套自己的理解；条目里没有的不加，条目里有的一条不少。写法见下一节。

## 转成 goal

goal 的停止判定是另一个模型读对话、对照 goal 原文判断「做完没有」：它看不到文件，只认 goal 里写成「满足」的状态，没写成满足的结束一律打回去继续。所以写 goal 时：

- **照抄每条的本机验收原文，不抄标题。** 标题和「要的结果」写的是终态，常常要部署后才看得到；判定者拿它对照，就会把部署时才做的部分判成没做到。部署时、别的主机上才能做的部分，另起一段写明「本次不在范围」。
- **给停下一个合法出口。** 条件里写明：以一行 `GOAL-STOP：<要ta决定的事>` 结尾的回复也算满足。不写，「停下来问」在机制里就不存在，每次停都被拽回去，最后只能应付判定者。
- **判定看文件，不看对话。** 要求把验收报告写进一个固定路径的文件：第一行「全部做到」或「部分失败」，每条一行，带证据文件路径。条件写成「这个文件存在、格式对、引用的证据文件都在」，不要求判定者从对话里认出证据（长对话会被压缩，证据在文件里）。
- **写死收敛规则。** 证伪最多两轮；会推翻某条验收的缺陷必须修，其余记进报告的「遗留」一栏，不修。不写，每轮证伪都能找到新东西，范围一直长。
- **每份 goal 都原样带上ta那段「be smart」。** 放在停下出口前面，一字不改：

  > be smart。希望你能正确判断什么是你应该自己拿主意，什么是应该停下来的。（但这个停下来绝不是给我弹一个询问弹框）你要停你就整个停。但是停本身并不是罪过。顶着错误继续干完才是。“继续和停下这两个按钮你都可以按，都是正当的，你自己要想清楚”

  执行方和判定者都读 goal 全文；出口规则说怎么停，这段说停不是失败。（「マスター」2026-10-24「要」）
- **派活上限只写ta给的数。** 宿主工具自带的默认规模（例如 Workflow 说明里的「medium：10 个以内」）不是ta的要求，不抄进 goal；抄进去就成了没人拍过板的魔法数字，还会被当成所有派活的总预算。ta给了上限，就写明它管的是 workflow 还是 specialist 座位。

## 验收报告

报告第一句给整体结论，只有两种：「全部做到」或「部分失败」。有一条不是「做到」，就是部分失败。然后逐条一行：

```text
R1  做到      证据：<路径 / 原始日志 / 截图>
R2  失败      原因：<发生了什么>  归因：实现 / 文档  下一步：<谁做什么>
R3  部分失败  做到的：<…>  没做到的：<…>  归因：实现 / 文档
```

不要用「基本完成」「主体完成」「剩余为后续」去盖住没做到的条目。部分失败如实写出来，下一轮就有明确的修补对象；藏起来，它会在用的时候才暴露。

## 变更

- 条目改动写进文档末尾的变更记录：日期、哪一条、拍板人原话。
- 推迟的条目不删，标「推迟」，写明什么事件发生时恢复、谁来判断。
- 背景记录可以随时加；条目只能经拍板改动。

## 示例

**反例**（2026-10-19 实际发生的写法）：

> §16 去工作区化与常驻架构裁决
> Q1 主线形态 → A. 单一永久主会话：唯一一条永久主会话正式立项推进；配套解决 #7（冷加载尾部 O(1) 按需读取 + cwd/pageOut 折叠状态快照 Checkpoint）与 #4（低频攒批卸载……）。

问题：标题的「去工作区化」没有任何条目承载；一条捆了五件事；「#7」「#4」没有定义；没有验收；没写桌面、无头哪边要。实现方因此只交付了能对上字面验收点的那几件（重启续接、checkpoint、攒批），「单一会话入口」和「去工作区」没人做，「尾部加载」被单方面挂成以后再做。

**正例**（同一意图拆成条目）：

```text
R1  示例聊天应用 只有一条永久主会话
要的结果：打开 示例聊天应用（桌面或无头）直接进入同一条主会话，不需要也不能先选工作区
范围：chat preset 的桌面与无头；omni 不在本条
验收：新 home 首次打开、重启后再打开、换一台浏览器打开，三次进入的都是同一会话 id，界面上没有「选择工作区」
拍板：「マスター」2026-10-18「唯一一条永久主会话正式立项」

R2  工作目录是会话的状态，不是会话的归属
要的结果：在主会话里切换工作目录，会话 id 不变，重启后仍在切换后的目录
范围：同 R1
验收：cd 到 A → 重启 → pwd 为 A，会话 id 不变
拍板：同上

R3  重启后冷开主会话不随会话长度明显变慢
要的结果：……（写清楚可以接受的耗时上限和测量方法）
```
